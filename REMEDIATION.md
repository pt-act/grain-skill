# Remediation Spec

**Purpose:** close the gap between grain-skill and the taste-skill repo it was
modeled on, so the project reads as a complete product rather than a sample.

**Grading baseline:** taste-skill ~8.5/10 as a product; grain ~6/10. The core
skill engineering is at parity or better (zero-dep inspector, state store,
doctor/report/tokens, CI harness). The gap is **breadth and surface area**, not
core quality.

**How to use this spec:** each item has an ID, a description, acceptance
criteria, and dependencies. Items are ordered by tier then by dependency. Check
off items as they land. Nothing here changes the existing pipeline — all of it
is additive.

---

## Tier 1 — Surface completeness

*Makes the repo look finished. Highest ROI. None of it is thrown away when
Tier 2 lands.*

### T1.1 — CHANGELOG.md + library versioning

**What:** A `CHANGELOG.md` at the repo root tracking releases. A `version`
field in `library/version.js` recorded into every dealt sheet, so a sheet
reprinted after a `git pull` warns if the library changed underneath it.

**Why:** the original has one; it's the cheapest maturity signal there is, and
it makes the library reproducible (seed + version → same sheet forever).

**Acceptance criteria:**
 [ ] `CHANGELOG.md` exists with an Unreleased section
[ ] `library/version.js` exports a semver string
[ ] `draw.mjs` records `libraryVersion` in the sheet and state
[ ] `draw.mjs --show` warns when the stored sheet's version ≠ current
[ ] `tokens.mjs` prints the version in its header comment

**Dependencies:** none.

### T1.2 — llms.txt machine-readable index

**What:** `llms.txt` at the repo root: a plain-text index of every skill
(install name, one-line description, path to SKILL.md) plus the script
surface. The original ships one; agents and humans both use it to discover
what the repo provides.

**Acceptance criteria:** [ ] `llms.txt` lists all 3 current skills with install
names and descriptions
[ ] lists all scripts with one-line purposes
[ ] regenerated by `scripts/llms.mjs` (run in CI or pre-commit)
[ ] stays in sync when skills are added (CI check or test assertion)

**Dependencies:** none.

### T1.3 — Plugin manifests (Claude + Codex)

**What:** `.claude-plugin/marketplace.json` and `.codex-plugin/marketplace.json`
at the repo root, plus the plugin metadata the marketplaces expect, so the
repo can be installed with `/plugin marketplace add` in Claude Code and
`codex plugin marketplace add` in Codex. Today the only install path is
`install.sh`.

**Acceptance criteria:** [ ] `.claude-plugin/marketplace.json` exists with
`name`, `description`, `owner`, and a skills array pointing at `skills/*/SKILL.md`
[ ] `.codex-plugin/marketplace.json` exists in Codex's expected shape
[ ] `install.sh --list` output matches the marketplace skill list
[ ] a fresh clone installs via the marketplace path (manual smoke test
documented in the README)

**Dependencies:** none. (T1.2 should land first so llms.txt and the
marketplace list stay in sync.)

### T1.4 — Committed example evidence

**What:** each example in `examples/` ships its own proof: the dealt
direction sheet, the critique, and the picture credits. Today the pages exist
but the evidence of *how they were built* is not committed, so the examples
assert rather than show.

**Acceptance criteria:** [ ] `examples/wine-bar/SHEET.md` — the dealt sheet
(palette, type, hero, blueprints, motion) as dealt by `draw.mjs`
[ ] `examples/wine-bar/CRITIQUE.md` — the fourteen-pass critique with a score
[ ] `examples/wine-bar/CREDITS.md` — picture credits in the footer format
[ ] same three files for `mountain-hut` and `studio`
[ ] `examples/README.md` links to each example's evidence
[ ] a `make examples` or `scripts/examples.mjs` regenerates sheets/credits
from the committed pages (dogfooding the pipeline)

**Dependencies:** none. (T1.1's versioning makes the sheets reproducible.)

### T1.5 — Root tests/ layout

**What:** the original keeps `tests/` at the repo root. Grain keeps them
inside `skills/grain/tests/`. Mirror the original layout so the repo scans
familiar: root `tests/` with the fixtures and runner, and the in-skill tests
become a thin wrapper or move up.

**Acceptance criteria:** [ ] `tests/fixtures/` at repo root (clean + sloppy
pages, images)
[ ] `tests/run.sh` at repo root, path-independent
[ ] `skills/grain/tests/` removed or reduced to a README pointing up
[ ] CI workflow updated to the new path
[ ] `run.sh --skip-browser` still passes locally; full run passes in CI

**Dependencies:** none.

## Tier 2 — Real breadth

*Closes the product gap. Each item is a new skill or a new capability that
the original has and grain doesn't.*

### T2.1 — output-skill (half-output enforcement)

**What:** a small meta-skill for the common failure where the model ships
half-finished work — truncated files, `// TODO` placeholders, "the rest is
left as an exercise." Rules for full output: no placeholder comments, no
truncated functions, every section the brief asked for present and complete.

**Why:** the original ships this as a standalone skill; it's one of the
highest-value meta-skills and it's tiny.

**Acceptance criteria:** [ ] `skills/output-skill/SKILL.md` with frontmatter
`name: grain-output`
[ ] rules for detecting and refusing half-finished output
[ ] a checklist the agent runs before declaring any build done
[ ] listed in `llms.txt` and the marketplace manifests
[ ] a test fixture: a half-finished page that the skill's checklist catches

**Dependencies:** T1.2, T1.3 (so it's discoverable).

### T2.2 — image-to-code skill

**What:** a skill that takes a reference screenshot or design image, analyses
it (layout, type, colour, spacing, components), and produces a build spec
the coding agent follows. The original's version generates site references,
analyses them, then builds to match.

**Acceptance criteria:** [ ] `skills/image-to-code/SKILL.md` with frontmatter
`name: grain-image-to-code`
[ ] an analysis pass: what the reference does well, what it is made of
[ ] a spec pass: tokens, sections, components, content gaps
[ ] a build pass: the coding agent builds to the spec, then the gate runs
[ ] works with a local image path or URL
[ ] listed in `llms.txt` and marketplaces

**Dependencies:** T1.2, T1.3. (T2.1 is independent and can land first.)

### T2.3 — GPT/Codex stricter variant

**What:** a variant of the main skill for GPT and Codex that tightens the
rules where those models are weakest: more layout variance, stronger motion
direction, explicit anti-slop reinforcement. The original ships
`gpt-tasteskill` for exactly this.

**Acceptance criteria:** [ ] `skills/grain-gpt/SKILL.md` with frontmatter
`name: grain-gpt`
[ ] reuses the grain library (directions, palettes, heroes, sections)
[ ] adds the stricter rules as a delta, not a fork
[ ] the delta is data-driven (a `strict` flag in `draw.mjs` or a separate
rules file) so it doesn't fork the pipeline
[ ] listed in `llms.txt` and marketplaces

**Dependencies:** T1.2, T1.3. (T1.1's versioning helps here — the variant
pins a library version.)

### T2.4 — imagegen-frontend-web skill

**What:** a skill that produces design *images* (hero, landing page,
multi-section comps) for use with ChatGPT Images, Codex image mode, or any
image-capable agent — the original's most distinctive product line. Grain has
no imagegen surface at all.

**Acceptance criteria:** [ ] `skills/imagegen-web/SKILL.md` with frontmatter
`name: grain-imagegen-web`
[ ] prompt recipes for hero, landing page, and multi-section comps
[ ] the recipes encode the house rules (no gradients, no glass, real
photography direction, two typefaces)
[ ] a handoff section: how to pass generated frames to the coding agent
[ ] listed in `llms.txt` and marketplaces

**Dependencies:** T1.2, T1.3.

### T2.5 — brandkit skill

**What:** a skill that produces brand-kit boards — logo directions, palettes,
type pairings, applications — as design images. The original ships this as a
standalone.

**Acceptance criteria:** [ ] `skills/brandkit/SKILL.md` with frontmatter
`name: grain-brandkit`
[ ] board recipes: logo directions, palette, type, application mockups
[ ] reuses the grain palette and type-system libraries
[ ] listed in `llms.txt` and marketplaces

**Dependencies:** T1.2, T1.3. (T2.4 first — brandkit reuses its prompt
patterns.)

## Sequencing

```text
T1.1 ─┬─ T1.2 ─┬─ T1.3 ─┬─ T2.1 ─┬─ T2.2
      │        │        │        └─ T2.3
      │        │        └─ T2.4 ─── T2.5
      │        └─ T1.4
      └─ T1.5
```

**Suggested order:** T1.1 → T1.2 → T1.3 → T1.4 → T1.5 (Tier 1 complete, repo
looks finished) → T2.1 → T2.2 → T2.3 → T2.4 → T2.5 (Tier 2 complete, product
gap closed).

**Definition of done for the whole spec:** an outsider comparing the two repos
sees comparable breadth (skill count within ~2, same install surfaces, same
example evidence, same root docs) and grain's core-engineering advantages
(state store, doctor/report/tokens, CI harness) are still there and
documented.

## Open questions

1. **Legacy versions.** The original keeps `taste-skill-v1` and
   `taste-skill-v2-experimental` for backwards compatibility. Should grain
   adopt the same policy (keep renamed skills as aliases) or stay clean?
   *Recommendation: stay clean — grain is pre-1.0, nothing depends on it yet.*

2. **Sponsor/banner assets.** The original has `assets/readme-banner.webp`
   and sponsor logos. Cosmetic. *Recommendation: skip unless the project
   grows a sponsor base.*

3. **research/ directory.** The original has one. Grain's `library/sites.js`
   is the analogue but thinner. *Recommendation: fold a short `RESEARCH.md`
   into the repo when T2 lands, documenting what the studied sites showed.*
